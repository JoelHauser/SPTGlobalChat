# SPT Global Chat -- working notes for Claude

A chat box for SPT that talks to every other player with the mod: docked on the main
menu, an overlay in raid. Two halves:

- **relay/** -- a Cloudflare Worker routing to one Durable Object (`Room`) that holds
  every WebSocket through the Hibernation API and repeats accepted messages to all.
- **plugin/** -- a BepInEx client plugin (net472) that keeps one connection open and,
  from phase 2, draws the chat box.

**Shelved 2026-10-01, at the end of phase 1's code** -- by the user's choice, not
because anything failed. Nothing has been deployed or run in game. To resume: upgrade
Node to 22+, `wrangler deploy`, put the URL in `RelayConnection.ReleaseUrl`, and work
through *Untested, and what to look for first* below.

**There is no SPT server mod, on purpose.** The messenger is not reachable in raid, so
the client has to draw its own box; once it does, it also serves the menu. And under
Fika several players share one SPT server, so a server-side connection would have to
untangle who said what. A client plugin is always exactly one player.

SECURITY.md is the threat model and the release checklist. **Read it before changing
anything that touches the network, the login or the text path.** docs/PROTOCOL.md is
the wire format.

## Decisions, and why

- **websocket-sharp, not `ClientWebSocket`.** EFT ships `websocket-sharp.dll`
  (1.0.2.35012) in `Managed`, so nothing extra is shipped. It takes a per-connection
  certificate callback; net472's `ClientWebSocket` only obeys the process-wide
  `ServicePointManager` callback, which any mod can set to accept everything. SPT's own
  client plugins use Unity `CertificateHandler`s (per request) and do not touch the
  global one -- checked by string scan of spt-*.dll, not by decompiling.
- **websocket-sharp's default certificate callback accepts every certificate.**
  `RelayConnection.StrictCertificate` must always be set on a `wss://` socket. If a
  *valid* certificate fails in game (Unity's Mono and its root store), the fix is to
  pin the relay's public key -- never to accept errors.
- **The relay address is a constant**, `RelayConnection.ReleaseUrl`, still a
  `REPLACE-ME` placeholder (the plugin refuses to connect to it). A configurable address
  is one a scam guide can tell players to change. DEBUG builds get a
  `[Development] RelayUrl` that accepts only loopback.
- **Off by default** (`[General] Enabled = false`).
- **Token in the first frame**, never the URL or a cookie. See SECURITY.md.
- **`ALLOW_ANONYMOUS = "true"`** in `wrangler.jsonc` is phase 1 only, so the relay can
  be exercised before Discord login exists. It must be `"false"` before the relay
  address is given to anyone.
- **Two cleaners, one set of cases.** `relay/src/clean.ts` and `plugin/TextSafety.cs`
  are tested against `docs/clean-cases.json`, generated by `make-clean-cases.mjs` so
  the JSON is all escapes. Edit the generator, never the JSON.

## Traps hit while building this

- **The Write/Edit tools turn `\uXXXX` (U+0080 and up) into the real character.**
  Escapes in source came out as literal U+2028 (which ended a regex literal and broke
  the build), U+202E, U+FEFF, U+FFFF and U+FFFD. Control-range escapes survived.
  Every source file here is meant to be plain ASCII -- an invisible bidi character in
  source is the exact hazard the cleaner removes. Write escapes doubled inside strings
  (`"\\u202e"`, which both JS `RegExp` and .NET `Regex` read as an escape), or generate
  the file. Check with a byte scan for anything over 0x7E after writing.
- **NFC folds a mark before the cap counts it.** `e` + U+0301 becomes U+00E9, so
  `e` + four marks keeps *two more* marks after the fold. The first test expected
  otherwise; the test was wrong. The cap case now uses `x`, which has no precomposed
  forms, and the folding is its own case.
- **.NET `string.Normalize` throws on a lone surrogate**; JS `normalize` does not. Both
  cleaners strip lone surrogates first.
- **Newtonsoft replaces a lone surrogate escape with U+FFFD while parsing**, so on the
  relay path the plugin never actually sees one -- pinned by
  `TheGamesParserNeverDeliversALoneSurrogate`. It also means the tests cannot load the
  shared cases through Newtonsoft (or System.Text.Json, which refuses them); they
  decode the JSON escapes themselves.

## Phases

1. **Relay that repeats; plugin that connects.** *Code done, never run.* The relay
   passes tsc and 19 tests; the plugin builds (Release and Debug, 0 warnings) and its
   cleaner passes 21 tests. Nothing has been deployed and the plugin has never been
   loaded in game. Phase 1 shows chat in the BepInEx log and sends from
   `[Phase 1] Say` in the Configuration Manager; both go when the chat box exists.
2. **Main-menu chat box.** Own `Canvas` (Screen Space Overlay), `ScrollRect`,
   `InputField`, rich text off on every text component. Hidden in raid: find
   `Comfort.Common.Singleton<EFT.GameWorld>.Instantiated` by reflection.
3. **Discord login.** `/login/start`, `/login/:id` (shows the confirmation code),
   `/login/callback`, `/login/poll`; sessions hashed in the Room's SQLite; DPAPI on the
   plugin side; `ALLOW_ANONYMOUS` to `"false"`.
4. **Hardening.** Per-user rate limits, history (last 100), bans/mutes, admin commands
   from Discord ids in an env var, `/forgetme`.
5. **In-raid overlay.** Fade-in lines, a key to open input, cursor saved and restored,
   and a Harmony patch so typing does not reach the character. Read how Fika's in-raid
   chat blocks input before writing that patch; check its keybind for a clash.
6. **Release.** SECURITY.md checklist, README, sp-mod.com's rules on networked mods,
   moderators before announcing.

## Untested, and what to look for first

1. **Does websocket-sharp connect from inside EFT at all**, and does a valid Cloudflare
   certificate pass `StrictCertificate`? The first in-game run answers both. Then the
   badssl checks in SECURITY.md.
2. **Does `OnClose` fire after a failed connect** in this websocket-sharp build? The
   reconnect loop depends on it. If only `OnError` fires, the plugin stops retrying.
3. **`ConfigEntry.SettingChanged` re-entering** when `SayFromConfig` clears the value --
   harmless by reading, unconfirmed.
